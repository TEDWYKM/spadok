## 1. Навіщо сервер узагалі

Не «щоб синхронізувати між пристроями». Головна причина одна:

**Правило 1 зараз не захищене.** Гейт «оцінити можна лише з місця»
живе на телефоні. Для локального застосунку це чесно: людина може
обдурити тільки себе. Але щойно оцінки стають спільними, клієнтська
перевірка не варта нічого — підробити виклик зможе будь-хто за вечір.
А рейтинг мандрівників це прямий стимул так і зробити.

Тобто без сервера соціальний шар не «гірший», а безглуздий: він
рахуватиме довіру там, де довіряти нічому.

Друга причина: **каталог точок перестане жити в `data.js`.** Сьогодні,
щоб змінити статус пам'ятки на «зачинено», треба випустити реліз.
Коли точки переїдуть на сервер, перевірка статусів стає редакційною
роботою, а не інженерною — і етап 1 плану (фундамент даних) нарешті
має де відбутися.

## 2. Чим доводиться заплатити

Це варто прочитати до того, як писати перший рядок коду.

**Застосунок перестає бути чесним автоматично.** Зараз він чесний
за побудовою: нічого не покидає пристрій, і сказати про це можна
одним рядком. З сервером він стає розпорядником чужих даних, і
чесність доводиться підтримувати правилами, а не архітектурою.

**У Google Play змінюється три речі.** Data safety з «нічого не
збираємо» перетворюється на збір. З'являється обов'язкове видалення
акаунта — і в застосунку, і за вебадресою. З'являється політика
UGC: умови використання, скарга на контент і на користувача,
блокування користувача, реальна модерація з діями за нею.

**І головне.** Публічний профіль зі списком, де людина була і коли,
це історія переміщень. Ми щойно винесли в правило, що навіть у
власному кабінеті координат не зберігаємо. Робити цю ж історію
публічною за замовчуванням було б дивно — тому нижче видимість
вимкнена, а список відвідин не публікується взагалі.

## 3. Модель даних

```sql
account
  id            uuid primary key
  created_at    timestamptz
  name          text                    -- може бути порожнім
  mark          text                    -- знак мандрівника
  public        boolean default false   -- видимість профілю
  banned_at     timestamptz

device
  id            uuid primary key        -- анонімний вхід без пошти
  account_id    uuid → account
  first_seen    timestamptz
  last_seen     timestamptz

point
  id            text primary key
  region        text
  lat, lon      double precision
  status        text                    -- ok | warn | closed | occupied
  status_at     date                    -- та сама дата перевірки
  ...           решта полів каталогу

visit
  account_id    uuid → account
  point_id      text → point
  at            timestamptz
  verified      boolean                 -- підтверджено GPS чи вручну
  accuracy_m    int
  primary key (account_id, point_id)

vote
  account_id    uuid
  point_id      text
  value         smallint                -- +1 | -1
  reason        text                    -- обов'язковий при -1
  at            timestamptz
  primary key (account_id, point_id)
  foreign key (account_id, point_id) references visit (account_id, point_id)

comment
  id            uuid primary key
  account_id    uuid
  point_id      text
  body          text
  at, edited_at timestamptz
  hidden_at     timestamptz             -- сховано модерацією або скаргами
  foreign key (account_id, point_id) references visit (account_id, point_id)

comment_vote
  account_id    uuid
  comment_id    uuid → comment
  value         smallint
  primary key (account_id, comment_id)

report
  id, account_id, target_type, target_id, reason, at, resolved_at

point_score      point_id, up, down, score, updated_at
account_score    account_id, checks, comments, karma, updated_at
```

### Правило 1 як зовнішній ключ

Найважливіший рядок у всій схемі:

```sql
foreign key (account_id, point_id) references visit (account_id, point_id)
```

Голос і коментар **фізично не можуть** існувати без відвідин тієї самої
точки тим самим акаунтом. Це не перевірка в коді, яку можна забути
під час рефакторингу, і не політика доступу, яку можна відключити —
це обмеження бази. Спроба записати голос без відвідин падає на рівні
двигуна.

У цьому проєкті вже є звичка доводити правила до перевірок. Тут
випадає рідкісна нагода довести правило до структури.

### Чого в `visit` немає

Координат. Сервер отримує їх у момент підтвердження, міряє відстань
до точки, записує `verified = true` — і **викидає**. Лишається
«був у цій точці тоді-то» і похибка GPS, за якою можна судити про
надійність підтвердження.

Це продовження правила 6 на сервер. Різниця між «був у точці такого
дня» і журналом переміщень у наших умовах може виявитись дуже великою.

## 4. Популярність місця

### Чому не «плюси мінус мінуси»

Проста різниця винагороджує прохідність, а не якість. Площа Ринок із
4000↑/1000↓ обжене забуту фортецю з 50↑/0↓ — тобто рейтинг працюватиме
проти того, заради чого існує застосунок.

### Що замість

Нижня межа довірчого інтервалу Вілсона для частки схвалення:

```
p̂ = up / n,   n = up + down,   z = 1.96  (95%)

score = (p̂ + z²/2n − z·√( p̂(1−p̂)/n + z²/4n² )) / (1 + z²/n)
```

Простою мовою: «яка частка відвідувачів схвалює цю точку — з поправкою
на те, наскільки ми в цьому впевнені». Мала вибірка притягується до
середини, тож 3↑/0↓ не б'є 4000↑/1000↓, але й 50↑/0↓ не програє
автоматично тільки через розмір.

Рахується на запис у `point_score`, не на читання.

### Що бачить людина

Не `score`. Число має бути зрозумілим: **«82% з 61 відвідувача радять»**.
Сам `score` лишається сортувальним, службовим.

Поки голосів менше п'яти — не показуємо відсоток узагалі, пишемо
«ще мало оцінок». Відсоток від трьох голосів створює хибну впевненість.

### Мінус із причиною

Голий мінус і є замовчаний мінус: він каже, що щось не так, і не каже
що. Тому `reason` при `-1` обов'язковий, і список короткий та конкретний:

| Причина | Що робить застосунок |
|---|---|
| Зачинено, не пускають | N таких за короткий час → статус у чергу перевірки, попередження наступному |
| Дорога вбита | Позначка в картці; впливає на попередження перед виїздом |
| Майже нічого не збереглося | Нічого автоматичного — але чесно видно в картці |
| Платно й не варте того | Те саме, плюс сигнал для опису |
| Небезпечно | Найвищий пріоритет модерації, показується в картці одразу |
| Опис не відповідає дійсності | У чергу редагування каталогу |

Так downvote перестає бути анонімним невдоволенням і стає сигналом,
з яким можна щось зробити. Це, по суті, зрощення оцінки з наявною
кнопкою «Повідомити про проблему» — вони й так робили одне діло.

## 5. Коментарі й модерація

Обов'язки Google Play для застосунків із чужим контентом: умови
використання перед першою публікацією, скарга на контент **і на
користувача**, блокування користувача, модерація з реальними діями.
Це не разова робота — це щоденна.

Мінімальний працездатний набір:

- умови використання на першій публікації, з фіксацією згоди;
- скарга на коментар і на автора з інтерфейсу;
- блокування: заблокований автор зникає з вашої стрічки;
- автоприховування за N скарг до розгляду — краще прибрати зайве
  й повернути, ніж лишити висіти;
- ліміт частоти: не більше кількох коментарів на годину з акаунта;
- черга модератора з простим вебінтерфейсом.

### Що тут «допис»

Памʼятка і є тема, під нею — гілка. Ніхто не створює нових тем, тож
модерація втричі легша за форумну, а кожне слово прив'язане до місця,
яке людина бачила. Ні стрічки, ні підфорумів, ні публікацій ні до чого
не прив'язаних — це свідоме звуження, а не брак часу.

### Голос за коментар вимагає відвідин

Рішення ухвалене; ціну треба назвати чесно: голосів буде помітно менше,
бо оцінити корисність тексту можна й не бувши на місці, а на рідко
відвідуваних точках коментарі лежатимуть узагалі без голосів.

Але інакше карма стає найлегшою мішенню для накрутки в усій системі,
а разом із нею — і репутація мандрівника. І головне: карма тоді почала б
міряти вміння писати, а не те, чи правда написане. У Спадку все, що
впливає на інших, робиться з місця — без винятків.

**Свій коментар не піднімають.** Реддіт ставить автору плюс автоматично;
тут карма означає «інші вважають це корисним», тож власний голос зробив
би її самопроголошеною.

**Рахунок коментаря ховається на перші години** після публікації. Ранній
випадковий мінус тягне за собою решту — це добре відомо саме з Реддіта,
і лікується тим, що першим читачам просто немає на що орієнтуватись.

## 6. Репутація мандрівника

**Не за кілометри.** Таблиця «хто відвідав більше точок» винагороджує
накат: більше і швидше їздити, зокрема тоді, коли їхати не варто.
Для застосунку, який возить людей по країні під час війни, це єдина
форма рейтингу, якої треба уникати.

Рахуємо внесок:

| Лічильник | Що це | Чому саме це |
|---|---|---|
| `checks` | **підтверджені** оновлення статусів | Головний ризик проєкту — контент, а не код. Це механізм, який б'є саме в нього |
| `comments` | коментарі, які не приховані | Кількість без ваги нічого не варта, тому далі |
| `karma` | сума плюсів за коментарі від тих, хто там був | Оцінює користь, а не активність |
| `photos` | принесені фотографії | Коли з'являться — найдорожча стаття проєкту |

**Карма за статус нараховується після підтвердження, а не за саме
твердження.** Статус точки — це те, через що люди їдуть або не їдуть
за сто кілометрів; винагороджувати неперевірене твердження означало б
платити за здогадку. Механіка проста: другий, хто скаже те саме про ту
саму точку протягом 60 днів, підтверджує і себе, і першого, і статус
точки міняється. Модератор може підтвердити окремо. Побічний наслідок
приємний: накрутити карму, позначивши «зачинено» на всіх точках поспіль,
не вийде — потрібен хтось другий, хто справді там був.

Форма рейтингу теж має значення:

- **сезони, а не вічний топ.** Вічна таблиця назавжди належить тому,
  хто почав першим, і демотивує решту;
- **область, а не країна** — за замовчуванням; своя область цікавіша
  й досяжніша;
- **збірки замість нескінченного лічильника**: «уся Львівщина»,
  «усі бастіонні фортеці» — обмежені цілі, а не гонка.

## 7. Приватність

- **Видимість профілю вимкнена за замовчуванням.** Вмикається руками.
- **Що публічно, коли ввімкнено:** ім'я, знак, лічильники внеску,
  коментарі. **Список відвідин із датами не публікується ніколи** —
  це і є історія переміщень.
- **Координати не зберігаються.** Ніде й ніколи, див. розділ 3.
- **Видалення акаунта:** шлях у застосунку плюс вебадреса — вимога
  Google Play. Видаляється все, крім тіла коментарів, які лишаються
  під підписом «видалений акаунт», щоб не рвати нитки обговорення.
  Це має бути прямо сказано в політиці конфіденційності, інакше
  видалення буде неповним і нечесним.
- **Регіон розміщення — ЄС.** Не формальність.

## 8. Контракт API

```
POST   /auth/device        → акаунт і токен без пошти
POST   /auth/link          → прив'язати пошту до наявного акаунта
GET    /me                 → профіль і лічильники
PATCH  /me                 → ім'я, знак, видимість
DELETE /me                 → видалення акаунта

POST   /visits             → {point_id, lat, lon, acc}
                             сервер сам міряє відстань; координати не зберігає
GET    /points             → каталог зі статусами
GET    /points/scores      → [{point_id, up, down, pct, n}]
PUT    /points/:id/vote    → {value, reason?}
GET    /points/:id/comments
POST   /points/:id/comments
PUT    /comments/:id/vote
POST   /reports            → скарга на коментар або автора
POST   /blocks             → заблокувати автора
GET    /leaders            → ?scope=region&season=
```

`POST /visits` — саме тут живе гейт. Клієнт не заявляє «я прибув»,
він надсилає координати, а рішення ухвалює сервер. Усе інше з цього
випливає.

### Вхід

Спершу **анонімний акаунт на пристрої**: нуль тертя, працює з першого
запуску, нічого не треба вигадувати. Пошта прив'язується пізніше й
добровільно — тоді, коли накопичене вже шкода втратити. Це знімає
найгіршу властивість реєстрації: вимагати її до того, як людина
зрозуміла, навіщо їй акаунт.

## 10. Схема, яку можна перевірити

Проєкт легко написати так, щоб він звучав переконливо і не працював.
Тому схема лежить окремим виконуваним файлом, а поруч — перевірки:

```bash
psql -f server/schema.sql -f server/test.sql
```

Двадцять перевірок, жодного мокання. Кожна або друкує «✓», або валить
скрипт. Що саме доводиться:

- вердикт без відвідин відхиляє **база**, а не застосунок;
- вердикт точці, де людина не була, теж;
- коментар без відвідин — теж;
- голос за коментар від того, хто там не був, — теж;
- голос із підміненою точкою — теж;
- голос за власний коментар — теж;
- мінус без причини, мінус із вигаданою причиною, плюс із причиною —
  усі три відхилені на рівні `check`-обмежень;
- одне повідомлення про статус карми не дає й статусу точки не змінює;
  друге, таке саме від іншої людини, підтверджує обидва й змінює статус;
- у таблиці відвідин немає стовпців `lat` і `lon` — це перевіряється
  запитом до системного каталогу, а не оком;
- профіль за замовчуванням непублічний.

І окремо — обіцянки розділу 4, справжніми числами:

```
wilson(3, 0)     = 0.438     три голоси не б'ють чотири тисячі
wilson(4000,1000)= 0.789
wilson(50, 0)    = 0.929     але й пʼятдесят одностайних не програють розміру
```

Схему прогнано на PostgreSQL 16. Її можна виконати в SQL-редакторі
Supabase так само, як локально, — і зробити це варто **до** оплати
хостингу, а не після.
